1 · Context & goal

The study is a 2 × 2 between-subjects design: feature interrelatedness (bridge: absent / present) × feature heterogeneity (low / high), testing a serial-mediation model interrelatedness → cognitive load → usability → continuance (H1–H4).

A first pilot (N = 12, 3 per cell) was collected on Prolific. The data are clean and valid (complete trails, attention checks passed, no straight-lining), but the analysis surfaced two design/measurement problems that would prevent the hypotheses from being fairly tested at scale. The goal of v2 is to fix those problems — to give H1–H4 a fair, well-powered, valid test, not to force a particular result. Pre-registration is recommended.

6 · Heterogeneity redesign — the C2 proposal

The problem, restated

A ride is a location/address-driven booking. Both current second services — Courier (send a package) and Eats (deliver food) — are also address-driven delivery tasks, so relative to a ride they sit at a similar "distance." Neither anchors an extreme, so participants perceive no difference in similarity (d ≈ 0.05). Better wording (C1) cannot fix a manipulation that is structurally flat; C2 changes the actual second-service tasks so low- vs high-heterogeneity are unmistakable.

Design tension to resolve. The bridge (interrelatedness) works by carrying data over — auto-filling the ride's address into the second service. The more heterogeneous you make that service (e.g. "pay a phone bill"), the less shared data there is to carry over, so the two factors start to conflict. A good C2 pairing keeps some shared element (address) while making the activity clearly different in kind.

Candidate service pairings

OptionLow heterogeneityHigh heterogeneityProsCons
A — Max contrast Ride → another ride / mobility (return trip, scooter) Ride → non-transport (pay a utility bill, mobile top-up) Strongest, unmistakable similarity contrast Breaks address carry-over in the High cells → the bridge manipulation weakens exactly where it's crossed with high heterogeneity
B — Balanced (recommended) Ride → another mobility booking (return ride / scooter) Ride → different but still address-anchored (grocery delivery, or a home service e.g. cleaning) Preserves address carry-over in all cells; clear activity difference Contrast is moderate, not extreme — must be validated
C — Minimal rebuild Replace Courier with a clearly-similar mobility task (return ride) Keep Eats (food) as the high-heterogeneity anchor Smallest engineering change (only the low service changes); keeps Eats flow Relies on "return ride vs food" being a big enough gap — uncertain
Recommendation: if C2 is needed, prefer Option B (keeps the bridge valid across all four cells while making the activities clearly different), with Option C as a lighter-weight fallback. Option A gives the cleanest heterogeneity contrast but compromises the interrelatedness factor.

Engineering scope (why C2 is a larger change)

Unlike C1 (text only), C2 means building new experiment surfaces:

  • New Service-2 flow components for the new task(s) (analogous to components/Service2Phase/Courier* / Eats*).
  • Updated condition config (docs/contracts/experiment-config.json, lib/experiment-config.ts) mapping G1–G4 to new services.
  • Re-implement the bridge / auto-fill + banner logic and event instrumentation for the new services.
  • New E2E tests and updated workflow/design docs.

Estimated: a multi-day build plus a theory decision about which pairing best embodies "heterogeneity."

7 · Decisions for the team

  1. Approve v2 item wording? Review §3 (reverse-coded PU/CI, split MC). Adjust any wording before deploy.
  2. Run the validation pilot as gate? Deploy v2, collect ~8–10/cell, and check on /stats: is PU/CI variance restored (SD ≥ ~1.0), and do MC-I and MC-H separate (target Δ ≥ ~1.5)?
  3. Is C2 needed? If MC-H is still flat after C1, commit to C2 and pick a pairing (A / B / C above). If it separates, no C2 needed.
  4. Pre-registration & appendix. Update the questionnaire appendix to v2 and pre-register the model + power targets before the full run.
